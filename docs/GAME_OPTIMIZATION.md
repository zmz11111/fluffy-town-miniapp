# Sprint 2.5 游戏系统优化建议

> 状态：仅供审核的设计建议。本阶段不修改 Sprint 2 代码、存档结构或第一章内容，不引入参考项目的代码和素材。

## 参考范围与适用边界

| 项目 | 已核实的设计做法 | 对本项目的启发 |
|---|---|---|
| [Antura](https://github.com/vgwb/Antura) | 将学习旅程分为阶段、学习块和游玩场次；核心系统按学习要求筛选词汇，再把题包交给小游戏；小游戏有统一的启动与结束接口。[旅程说明](https://antura.org/en/dev/game-modules/Journey)、[数据流](https://antura.org/en/dev/game-modules/DataFlow)、[小游戏接口](https://antura.org/en/dev/game-modules/MiniGame) | 借鉴“学习目标、题目供给、玩法呈现”分层，不照搬 Unity 架构或复杂的自动选题系统。 |
| [Mini Pets](https://github.com/melvincwng/mini-pets) | README 描述喂食、玩耍、清洁带来等级与外观变化。[项目说明](https://github.com/melvincwng/mini-pets#readme) | 借鉴“孩子能看见互动后的变化”。其定时照料机制不直接套用到儿童学习，也不把团团改成待照料宠物。 |
| [Pat Engine](https://github.com/prdoring/Pat_Engine) | README 说明以数据文件描述图形、音效与演出序列，并把通用运行层与具体游戏内容分开。[项目说明](https://github.com/prdoring/Pat_Engine#readme) | 借鉴可审阅的内容配置与轻量演出编排，不移植浏览器引擎、编辑器或美术资源。 |

以下“建议”均是对《团团和它的毛茸茸朋友》的推导，不代表三个项目已经实现了相同规则。团团继续是孩子的智能陪伴伙伴，不是宠物或老师；英语学习、剧情探索和温暖反馈仍是核心。

## 一、游戏循环

### 当前基础

Sprint 2 的第一章已形成“剧情进入第三幕 → 听音找图三轮 → 小游戏星星 → 继续剧情 → 章节星星与米米解锁”的闭环。`story-manager` 负责剧情游标与任务门槛，`games/find-cookie` 负责选择判断，`reward-manager` 负责按奖励 ID 去重。单词内容独立于页面和教材。[现有引擎说明](GAME_ENGINE.md)

### 建议的体验节奏

| 环节 | 建议 | 对孩子的直接感受 |
|---|---|---|
| 出发 | 每段故事先提出一个明确、短小的探索目标；团团以邀请语气说明“我们要找什么”。 | 知道为何玩这一轮，而非被要求刷题。 |
| 探索 | 一个场景最多承载一个主要学习任务；小游戏的词和图片服务当前线索。 | 故事与英语内容彼此呼应。 |
| 回应 | 任务结束后让剧情角色回应发现，例如米米根据图卡指出篮子；答错允许重听和提示。 | 选择改变了故事中的下一句话或线索呈现。 |
| 收获 | 首次完成给明确的小奖励与伙伴互动；重玩可练习，但同一奖励 ID 不重复领取。 | 能看到成长，也能放心复习。 |
| 休息或继续 | 章节结束提供“看看伙伴”“再听一次”“下次继续”等可选入口。 | 允许自主停下，不制造连续登录或限时压力。 |

这借鉴了 Antura 将游玩场次、结果和旅程位置连接起来的思想，但本项目先维持一章一任务的轻量节奏，不增加强制关卡串联。[Antura 应用流程](https://antura.org/en/dev/game-modules/ApplicationFlow)

### 后续优先验证

1. 让儿童试玩第一章，观察是否能说出“为何听这三个词”“完成后发现了什么”。
2. 记录每幕停留、重听和退出的位置，用匿名汇总判断流程是否过长；不以答错次数评价孩子。
3. 先优化对白、线索提示和章节结尾反馈，再考虑增加奖励种类或每日任务。

## 二、宠物系统与伙伴互动

### 身份边界

团团是平等的陪伴伙伴，不能因没有喂养、答错或暂时离开而“失望”。米米是橘色小猫侦探伙伴，现有 `friendship` 只表达相处进度，不能变成学习成绩。未来若加入真正的宠物养成，应另设宠物资料与状态，不复用团团的身份及评价文案。[团团规范](GAME_DESIGN.md)、[数据规范](DATA_STANDARD.md)

| 主题 | 建议规则 | 避免的问题 |
|---|---|---|
| 好感度 | 对米米等伙伴，按“共同完成章节、找到线索、主动打招呼”等有意义的事件增加关系；展示称呼、对白或小档案变化。设置清晰上限和去重规则。 | 反复点击刷数值、答错降低好感、以角色喜爱程度逼迫学习。 |
| 情绪 | 团团情绪保持情境性的短期表达，如好奇、担心、开心；转场或再次进入时由剧情情境决定，不做随时间衰减的照料负担。米米可有独立表情，但不推断孩子真实心情。 | 角色“生病”“孤独”等压力提示，以及长期负面状态。 |
| 成长 | 优先用剧情里程碑呈现，例如米米从“初识”到“侦探伙伴”，解锁新的对话或合照；以后真正宠物可用外观阶段成长。学习掌握度另由学习记录表达。 | 把等级、好感度和英语能力混成同一分数。 |
| 互动反馈 | 每次互动给简短、符合性格的回应；可按剧情阶段和最近事件切换有限对白池。答对强调“共同发现”，答错给重听或线索，不扣关系值。 | 机械重复、冷冰冰评分、老师式说教。 |

Mini Pets 的可见成长值得借鉴，但它 README 中的定时喂养/清洁属于虚拟宠物玩法。本项目若未来加入真正宠物，也应先评估儿童使用时长与照料压力，不把定时提醒作为推进英语学习的前提。[Mini Pets README](https://github.com/melvincwng/mini-pets#readme)

## 三、教材扩展能力

### 多教材、多年级、多章节

建议把“发布的内容包”和“孩子的学习进度”继续分开。内容包可有 `textbookId`、`edition`、`grade`、`semester`、`unitId`、`contentVersion`、`source`、`rightsStatus`、`reviewStatus`；词、音频、图片、任务、章节使用稳定 ID。下表是**将来内容发布时的字段建议**，不是要求现在修改存档。

| 扩展问题 | 建议 |
|---|---|
| 多教材 | 用教材/版本命名空间区分内容包；同一个英语概念可关联不同教材词条，但保留各自来源、页码、授权与审校记录。切换教材时先展示进度映射预览，不把同名词直接当作已掌握。 |
| 多年级 | 章节和题包声明适用年级、目标词与先备词；年龄更高时调整句长、干扰项和提示密度，团团的人格不变。年级选择由孩子/家长明确确认，不靠答题表现自动推断。 |
| 多章节 | 用章节清单声明顺序、前置条件、场景和任务引用；每章拥有独立进度与内容版本。新增章节优先增加经过审校的内容，避免把章节 ID 写死在页面。 |
| PDF 导入 | 按“确认使用权 → 抽取候选词句及页码 → 人工校对 → 匹配已授权音画素材 → 内容校验 → 版本发布”处理。PDF 原件与候选数据不直接写进儿童存档。 |
| 家长端 | 未来只读取经过授权的学习摘要、使用时长和内容来源；教材切换、数据删除等由家长确认，不开放直接修改奖励与剧情游标。 |

Antura 用学习层级和筛选条件控制词汇进入不同游玩场次，说明“同一玩法可服务多个内容阶段”；本项目可先用明确的年级、单元和目标词清单实现这一点，无需引入其完整 Teacher 系统。[Antura Journey](https://antura.org/en/dev/game-modules/Journey)、[Antura Data Flow](https://antura.org/en/dev/game-modules/DataFlow)

### 内容发布前的检查项

- 词条 ID、章节 ID 与版本唯一；引用的词、音频、图片和奖励均存在。
- 每个素材有来源及可用于小程序的许可；未授权第三方素材不得进入发布包。
- 题目正确答案唯一，干扰项适龄，音频与文本一致。
- 旧内容版本仍能解释已有学习记录；升级时有映射或保留旧版引用。

## 四、小游戏系统

### 减少重复代码的建议

保留现有 `games/find-cookie` 作为第一个具体玩法。后续可先抽象**小而稳定的共用约定**：任务资格、题包输入、开始/恢复、提交选择、鼓励反馈、完成事件、一次性奖励。题包只携带词条 ID、展示资源引用、正确项、可选干扰项和提示，不让页面或玩法代码直接读取教材 PDF 或写本地存储。这与 Antura 的题包供给思路相近。[Antura MiniGames Interface](https://antura.org/en/dev/game-modules/MiniGame)

| 增加内容的情况 | 推荐方式 | 新增代码量 |
|---|---|---|
| 同一“听音选图”玩法换章节、词或图片 | 新建经过校验的题包配置，复用界面与判定流程。 | 主要是内容。 |
| “看图选词”等仅呈现方向不同 | 复用题包字段和生命周期，增加少量展示适配。 | 少量玩法界面。 |
| 连线、排序等交互规则不同 | 增加一个独立玩法适配器，继续复用进度、反馈和奖励约定。 | 一份新的交互规则，不复制整个系统。 |

Pat Engine 将可变内容和演出序列写成可审阅的数据，为“同一机制换内容”提供参考；本项目只借鉴这种数据驱动思路。微信小程序的页面、音频和包体约束仍以项目自身需求设计，不引入它的浏览器运行时。[Pat Engine README](https://github.com/prdoring/Pat_Engine#readme)

建议先有 2～3 种经过儿童试玩验证的交互原型，再决定哪些字段值得共用。过早做万能玩法解释器，反而会让题目规则与反馈难以审查。未来所有小游戏继续经业务模块更新状态，页面不直接保存数据；奖励仍以稳定 ID 去重。

## 建议实施顺序与审核点

1. **先验证体验**：用现有第一章检查叙事衔接、重听、错误提示和结尾反馈；以儿童理解和完成感为依据。
2. **再整理内容规范**：确定教材包标识、版权/审校字段、题包校验和版本策略；先做少量人工维护内容。
3. **最后扩展伙伴与玩法**：选择一种伙伴里程碑反馈和一种新小游戏原型，分别评估儿童体验与开发成本。

本文件只提出候选方向。任何后续实现均应单独成 Sprint 审核，保留 Sprint 2 的第一章闭环及现有模块边界。
